## Environment variables

| Variable | Where | Notes |
|---|---|---|
| `PUBLIC_SUPABASE_URL` | build + admin | Safe to expose |
| `PUBLIC_SUPABASE_ANON_KEY` | admin | Safe to expose; RLS is what protects the data |
| `SUPABASE_SERVICE_ROLE_KEY` | **build only** | Full database access, bypasses RLS. Server-side only. Never in a `PUBLIC_*` var, never in a client bundle, never committed. |
| `DEPLOY_HOOK_URL` | admin server routes | Secret — anyone holding it can trigger builds |

Add `.env` to `.gitignore` and commit a `.env.example` with empty values.

## Build

```bash
npm ci
npm run build        # reads Supabase with the service role key, prerenders to build/
```

Output directory depends on the adapter (`build/` for `adapter-static`). Deploy that.

Verify after every build:
- page count matches (41 indexable + 404)
- `sitemap.xml`, `robots.txt`, `llms.txt`, `_redirects` are present
- **zero** occurrences of the Supabase URL in the output

## Publish flow

```
Niels edits in /admin
  → saved to Supabase (site unchanged)
  → clicks Publish
  → admin server route POSTs to DEPLOY_HOOK_URL
  → host rebuilds, reading Supabase
  → static output deployed  (~1 minute)
```

The deploy hook URL must be called from a **server route**, never from the browser.
Rate-limit it: a client who clicks Publish five times should trigger one build, not five.

## Redirects

16 rules, currently in Cloudflare `_redirects` format:

```
/diensten-one-man-agency    /diensten     301
/post/*                     /blog         301
```

10 static rules plus one per post `legacy_url`. Generate this file at build time from
Supabase so new posts with a `legacy_url` are covered automatically.

**On a different host this file does nothing.** Vercel needs `vercel.json`, Netlify uses
`_redirects` with different semantics. Resolve Q3 first.

## `_headers` — Q5

The original delivery had a Cloudflare `_headers` file; it was lost during a restructure and
was never generated by `build.py`. The site deploys fine without it, with host defaults.
If reinstated, it covers CSP, HSTS and cache-control — all decisions, not defaults to guess.
Ask before writing one.

## Pre-cutover checklist

Run on the staging URL, not locally:

- [ ] All 41 routes return 200; `/bestaatniet` returns the styled 404
- [ ] Logo in the top bar, white logo in the footer
- [ ] Hero is green with black text; Poppins loads (not a fallback)
- [ ] `/diensten/webdesign` works without `.html`
- [ ] `/sitemap.xml`, `/robots.txt`, `/llms.txt` all load
- [ ] Old URLs redirect: `/vragen` → `/veelgestelde-vragen`, `/webdesign` → `/diensten/webdesign`
- [ ] JSON-LD passes Google's Rich Results Test on home, a service page, a blog post
- [ ] Mobile menu opens and closes; `aria-expanded` flips
- [ ] Both forms submit (blocked until the Formspree ID is set — see Q1)
- [ ] `/admin` requires login; logged out, it redirects
- [ ] A full edit → publish → live cycle completes
- [ ] Lighthouse on mobile is no worse than the current static build

## Rollback

Keep the previous deployment available for instant rollback (Cloudflare Pages retains
deployments). Supabase content is not rolled back by a redeploy — a bad *content* edit is
fixed in the CMS, a bad *code* deploy is fixed by rolling back. Make sure you know which
you are dealing with before acting.
